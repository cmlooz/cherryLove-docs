# ADR-012 — Internationalization (i18n)

Implements: DEC-021, DEC-030, REQ-N-UX-03, REQ-F-ACC-04, REQ-F-HOME-01, REQ-F-NOTIF-01/02/05, REQ-F-AUTH-01/08,
REQ-N-ARC-06.
Builds on: ADR-002 §2 (`cherrylove-core/src/i18n/`), ADR-010 (errors translated client-side by `code`).

## Context

The UI ships in Spanish and English from v1, with no hard-coded strings; the user picks the language in their
account (REQ-F-ACC-04). Docs and code identifiers are English (DEC-030). User content (cards, notes, memories) is
never translated.

Text is produced in **two places**: the clients (all screens, error messages per ADR-010) and the server (invite
and recovery emails, push notifications, staff admin). Both need a source for the user's language.

## Decision drivers

1. One catalog shared by web and mobile; no string exists only in one app.
2. A missing translation fails CI, not a user.
3. Server-sent texts (email, push) use the recipient's language, even when they are offline.
4. Fewest dependencies (REQ-N-ARC-06): two languages, simple plurals.

## Options considered (client)

| Option | Verdict |
|--------|---------|
| `i18next` (+ `react-i18next` in apps) | ✅ Mature, works in web and React Native. ❌ Two dependencies and a plugin model for needs we do not have. |
| FormatJS / `react-intl` (ICU MessageFormat) | ✅ Full ICU. ❌ Heaviest; ICU is overkill for es/en. |
| Lingui | ✅ Compile-time catalogs. ❌ Build step in three repos. |
| **Own minimal translator in `cherrylove-core`** ⭐ | ✅ ~1 file: typed keys, `{param}` interpolation, `_one`/`_other` plurals. No dependency. ❌ We own it; no ICU features. |

## Decision

### 1. Client catalog (`cherrylove-core/src/i18n/`)

- `es.json` and `en.json`, flat keys `<module>.<screen>.<element>` (e.g. `cards.today.empty`), plus `errors.<code>`
  (ADR-010).
- TypeScript key type generated from `en.json`; `t("cards.today.empty")` with an unknown key does not compile.
- `t(key, params)`: `{name}` interpolation; plurals by suffix (`days_one`, `days_other`) chosen with
  `count === 1` — correct for both Spanish and English, no `Intl.PluralRules` needed.
- Dates and numbers: `Intl.DateTimeFormat` / `Intl.NumberFormat` with the active locale (`es-CO` / `en-US`).
  Hermes `Intl` coverage for these is verified in plan H before relying on it.
- Civil dates (DEC-024) are formatted as dates only — never converted through the device timezone.

### 2. Checks (CI in `cherrylove-core`)

| Check | Fails when |
|-------|-----------|
| Parity | A key exists in one language but not the other |
| Params | `{param}` names differ between `es` and `en` for the same key |
| Contract codes | An error `code` in the contract has no `errors.<code>` key (ADR-010 §6) |
| Unused keys | A key is referenced by no app (report, not failure) |

In web and mobile, ESLint `react/jsx-no-literals` (from `eslint-plugin-react`, already a standard React lint
dependency) forbids raw text in JSX (REQ-N-UX-03).

### 3. Which language is active

| Moment | Source |
|--------|--------|
| First launch / before login | Device locale: `es*` → `es`, anything else → `en` |
| After login | `user.language` from the account (server is the source of truth, REQ-F-ACC-04), stored locally for offline use |
| User changes it | Saved to the account; applied immediately on that device, on the next sync elsewhere |

### 4. Server-side texts

| Text | Language used | Mechanism |
|------|---------------|-----------|
| Push (REQ-F-NOTIF-01/02) | Recipient's `user.language` | Django `gettext` catalogs (`.po`) in the `notifications` module; generic copy only, never content (REQ-F-NOTIF-05) |
| Password recovery email | Account's `user.language` | Django `gettext` templates |
| Invite email (REQ-F-AUTH-01) | **Bilingual** (Spanish first, then English) | The invitee has no account yet, so no preference exists; one email serves both |
| Staff admin | Django's built-in translations + `gettext` in custom views | Staff may use es or en via Django's `LocaleMiddleware` |
| API `title`/`detail` | English only | Never shown to users (ADR-010) |

### 5. Copy that looks fixed but is not

REQ-F-HOME-01 writes the header as `"{user1.name} y {user2.name}"`. The `y` is Spanish copy, so it becomes the key
`home.header.names` (`"{a} y {b}"` / `"{a} and {b}"`). Same rule for the push text `"your card for today is
ready 🍒"` in REQ-F-NOTIF-01.

## Consequences

- ✅ One catalog for both apps; missing or mismatched translations break CI.
- ✅ Pushes and emails reach users in their language even if the device is offline.
- ✅ Zero new runtime dependencies.
- ❌ No ICU (gender, select, complex plurals); adding a third language with different plural rules means
  extending `t()` or adopting a library then (new ADR).
- ❌ Translations live in two formats (JSON for clients, `.po` for server texts).
- ⚠️ Bilingual invite emails are longer; accepted to avoid guessing the invitee's language.
