# ADR-003 — OpenAPI contract-first and versioning

Implements: REQ-N-ARC-02, REQ-N-ARC-03, REQ-N-ARC-04, REQ-N-ARC-07, REQ-N-QA-02, DEC-004, DEC-024, DEC-029.
Builds on: C4-001 (contract is the only line between clients and server), ADR-002 (`tests/contract/`, `core/src/contract/`).

## Context

Two frozen requirements pull in different directions:

- **REQ-N-ARC-03** — *contract-first*: the spec is decided first and is the only coupling.
- **REQ-N-ARC-02** — the spec is *generated* by drf-spectacular from DRF code (code-first tooling).

If the generated file *is* the contract, any refactor in a serializer silently changes what web and mobile
receive. This ADR reconciles both and fixes where the contract lives, how it is versioned, and how clients
consume it.

## Decision drivers

1. A contract change is a deliberate, reviewed act — never a side effect.
2. The code must provably honor the contract (machine check in CI).
3. Old mobile builds stay alive in users' phones; breaking changes must not strand them.
4. Few dependencies (REQ-N-ARC-06): tools at build time only, nothing at runtime if avoidable.

## Options considered

| Option | How | Verdict |
|--------|-----|---------|
| O1 — Code-first | drf-spectacular output is the contract. | ❌ Violates driver 1 and REQ-N-ARC-03. |
| O2 — Design-first + drift check ⭐ | A hand-authored `openapi.v1.yaml` is the approved contract. drf-spectacular still generates a spec from code; CI fails if generated ≠ approved. | ✅ Satisfies both REQs. |
| O3 — Design-first + server stub generation | Generate Django code from the spec. | ❌ Poor DRF fit, heavy generator, fights ADR-001 layers. |

## Decision

**O2.**

### 1. Where the contract lives

| Phase | Location | Why |
|-------|----------|-----|
| Now (session C) | `cherryLove-docs/04-architecture/api-001-openapi-v1.yaml` (API-001) | No code repos yet (DEC-033); approved like any doc. |
| After session R | `cherrylove-api/contract/openapi.v1.yaml`; docs keep a pointer | The contract travels with the code that must honor it, so one PR changes both and CI checks both. |

A PR that touches `contract/` is a **contract change**: it needs Camilo's explicit approval and cites
the REQ IDs it serves.

### 2. Checks in `cherrylove-api` CI

| Check | Tool | Fails when |
|-------|------|------------|
| Drift | drf-spectacular + a normalizing compare script | Generated spec ≠ `contract/openapi.v1.yaml` |
| Breaking change | `oasdiff breaking` (CI binary, not a Python dependency) | Contract PR breaks the last released contract inside the same major version |
| Lint | `oasdiff` / schema validation | Spec is not valid OpenAPI 3.1 |

### 3. Distribution to clients

1. On merge to `main`, API CI publishes the contract as a release asset tagged `contract-v1.MINOR.PATCH`.
2. `cherrylove-core` pins one contract version and generates `src/contract/` with **openapi-typescript**
   (types only, dev dependency, zero runtime). The client in `api-client/` is hand-written and thin.
3. A new contract version → a `cherrylove-core` release → web/mobile bump core. SemVer mirrors the contract:
   additive = minor, breaking = major.

Alternatives for codegen: full client generators (orval, openapi-generator) — rejected: large generated
runtime code and less control over auth, request_id, and Problem Details handling.

### 4. Versioning

- Path versioning: `/api/v1/…`. Inside v1 only **additive** changes (new endpoints, new optional fields,
  new enum values documented as open).
- A breaking change creates `/api/v2/` alongside v1. v1 keeps running and answers with `Deprecation` and
  `Sunset` headers until the sunset date approved by Camilo.
- Why path and not header versioning: visible in logs, caches and the browser; trivial for DRF routing.

### 5. Contract conventions (apply to API-001 and every later endpoint)

| Topic | Rule | Source |
|-------|------|--------|
| Field names | `snake_case` on the wire **and** in generated TS types; no case-transform layer | REQ-N-ARC-06 (no extra lib), one name to grep everywhere |
| IDs | UUIDv7 strings, generated by the client for syncable entities | REQ-F-SYNC-03 |
| Timestamps | ISO 8601 UTC with `Z` (`created_at`, `updated_at`) | — |
| Civil dates | `YYYY-MM-DD`, no time zone (relationship start, memory date, birth date) | DEC-024 |
| Lists | Cursor pagination: `{ "results": [...], "next_cursor": "…" \| null }` | REQ-N-PERF-02 |
| Errors | `application/problem+json` (RFC 9457); shape detailed in ADR-010 | REQ-N-QA-02 |
| Tracing | `X-Request-ID` header accepted and echoed | REQ-N-QA-01 |
| Operation IDs | `<module>_<verb>_<noun>`, e.g. `cards_list_today` — stable names for codegen | — |
| Tags | One tag per ADR-001 module | ADR-001 |
| Spec version | OpenAPI 3.1 | — |

## Consequences

- ✅ No accidental contract changes; refactors that alter the wire fail CI.
- ✅ Clients compile against a pinned, released contract; old mobile builds keep a working v1.
- ✅ Zero runtime dependencies added on the client for the contract.
- ❌ Every contract change touches two artifacts (YAML + code) — that friction is the point.
- ❌ `snake_case` in TypeScript looks unusual; accepted to avoid a mapping layer and a dependency.
- ⚠️ drf-spectacular output must be tuned (component names, enums) so the drift compare is stable;
  plan F budgets one step for this.
